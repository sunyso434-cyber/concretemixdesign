## 0. 摘要（一页结论）

**DSH 是什么**：DeepSeek Harness（`dsh`）是 DeepSeek 官方开源的 AI 智能体框架，**"一切皆插件"** 架构。它的 Web 界面（`npx @deepseek-ai/dsh web` 启动，本机 3080 端口正在运行的就是它）是其核心交互形态。项目 2026-08-13 上线 GitHub 后**爆火（两天内 7.3 万+ stars）**，目前为开发者预览版。

**DSH 页面输出的核心特色**（砼智值得学的）：
1. **工具调用卡片体系**：每种工具（读文件/搜索/命令/改文件/查网页）有专属可视化卡片（行号语法卡、匹配分组卡、终端卡、diff 差分卡、引用卡），全部可展开折叠
2. **每轮回复统计行**：LLM 耗时·工具耗时、TTFT（首 token 延迟）、tok/s、缓存命中率、输入/输出 token 数
3. **思考过程折叠行**：运行中扫描光效 + 流式显示最新一行思考内容
4. **上下文计量环 + 细分面板**（系统/工具/消息三段色条）
5. **消息操作**：复制/分支（fork 新会话）/时间戳/点赞点踩反馈
6. **轨迹视图（Trajectory）**：Chrome 开发者工具 Network 面板风格的操作时间线 + 事件账本 + 全文搜索 —— 即"轨迹"功能
7. **产出文件 chips**：每轮 AI 产出的文件聚合展示，点击跳转

**砼智现状**：已有流式聊天、思考折叠、工具气泡、进度卡、上下文圆环、Todo、业务结果卡（配合比/优化/报价）。差距主要在：无 token/耗时统计、工具卡较朴素、无单条复制/反馈/重试、**无轨迹视图**、卡内暂停按钮存在接线缺陷。

**轨迹功能可行性结论**：**可行，且砼智有独特优势**（timeline 数据已存在并已随消息落库 SQLite）。建议分三个阶段实施（最小版 2-3 天 → 增强版 1-2 周 → 时间线版 3-4 周），详见第 6 章。

## 2. DSH 页面输出方式全景

（详细代码依据见 docs/dsh-page-output-architecture.md，此处为提炼）

### 2.1 布局与组件机制

- **三列自适应布局**（AppFrame）：左侧栏 / 会话主体 / 右侧详情面板。中栏优先（<640px 时详情自动关闭），窄屏（<1024px）侧栏折叠为 56px 图标条。
- **插槽（slots）注册机制**：整个界面组件靠 `slots.inject + slots.register` 挂载，按 key 分派。聊天节点（assistant/工具/压缩/错误…）→ 对应 React 渲染组件；工具卡按工具名分派（`tool.call.toolview`），未匹配的落到通用卡。
- **数据流**：`useSession`（订阅会话快照）+ `useProjection`（订阅服务端投影，如 token 用量/上下文压力/目标/待办）+ 本地 store（草稿/选中态）。**"一切皆可投影、皆可订阅"** 是它不卡顿的架构基础。

### 2.2 会话消息流式渲染

- Assistant 消息按**块（blocks）**流式渲染：文本块→Markdown、思考块→折叠行、图片块→画廊、工具调用块→树状卡；`data-streaming` 标记运行态，中断时渲染灰色 "stopped"。
- 流式更新用**帧节流**（useThrottledVisualUpdate）：DOM 合并到帧间隔刷新，长输出不白屏。

### 2.3 思考过程展示

- "Think" 折叠行：默认只显示**首行**（流式时自动滚动显示**最新一行**），点击展开全文（等宽字体）；运行中有 2.6 秒扫描光效。

### 2.4 工具调用卡片体系（砼智最值得学的部分）

| 工具 | 专属卡片形态 |
|---|---|
| 读文件 | 带**行号 + 语法高亮**的代码卡（默认只展开 8 行），标题 `Read·路径` |
| 搜索（grep/glob） | **匹配分组**列表卡（按文件/路径分组），超限显示截断提示 |
| 查网页 | 引用来源列表卡（标题+URL+摘要）/ 抓取页卡 |
| 跑命令 | **终端卡**：命令、工作目录、输出、退出码（红色失败 pill） |
| 改文件 | **diff 差分卡**：hunk 前后对比（8 行内） |
| 提问用户 | 一行问题交互卡 |
| 待办计划 | 进度计数卡 `✓ done/total` |

统一外壳 ToolRow：`图标 + 标题 + 一句话摘要 + 状态点（成功/失败/警告）`，点击展开 body；运行中扫描光效。

### 2.5 回合统计与上下文计量

- **统计行**（每轮回复后）：`回合数/步数 | LLM 时长 · 工具时长 | TTFT · tok/s | 缓存命中% · in/out tokens`，溢出变 tooltip。
- **上下文计量**：发送键旁 28px 环形圆显示占用 %；点击弹细分面板，system/tools/messages 三段色条。
- **压缩提示**：上下文压缩（compaction）作为节点展示生命周期；注入式上下文（技能/工作区指令）折叠成一行（角色+来源）。

### 2.6 消息操作与反馈

- 每条消息：**复制 / 分支（fork 会话，从该消息起新开）/ 时间戳**（用户与 AI 时钟位置镜像）；AI 消息追加 `· Ran for 15s`、`· TTFT`、`· 34 tok/s`。
- **点赞/点踩 + 附注**反馈按钮；审批面板（shell 命令确认）；重试按尝试链折叠展示。

### 2.7 轨迹视图（Trajectory）

会话上方 tab 切换到"**轨迹**"视图，把本次 AI 工作的全过程变成一个**可检查、可搜索、可回放**的账本（该视图为独立前端包 `ui-trajectory`，数据来自与 Chat 共享的会话事件窗口，**纯浏览器渲染、不进入模型请求**）：

- **事件账本（Ledger）**：按 Turn（回合）分组，每回合内 Message/Step 分组；每条记录一行：`#序号 + 类型图标 + 一句话摘要 + 耗时`，点击行弹出**详情检查器**（输入/输出/思考全文/工具 schema/精确耗时/token 明细）。
- **记录类型**：system（系统提示词快照）/ user / context（上下文注入）/ compacted（压缩）/ message（AI 消息）/ tool / subtool（工具及子工具调用）。
- **Chrome Network 风格时间线**：顶部 Overview 横条从左到右投影各记录的真实开始时间与耗时，每条操作一个色块，**4 种投影模式**（按顺序等宽 / 真实耗时 / 压缩空闲的时间 / 真实墙钟时间）；**助手时间条区分 TTFT（首 token 延迟）与解码时间**，悬停 500ms 显示精确时刻；支持**滚轮缩放、拖拽平移、拖选区间聚焦**（高亮区间内所有记录）、右键清除/平移、点击色块跳到对应记录；三车道自动布局（lane）。
- **实时搜索**：全文增量索引（变更后 3 秒批量提交，只在一个记录源变化时重新解析 Markdown），空格分隔多词搜索，命中行高亮。
- **折叠控制**：全部回合折叠/展开、全部工具调用折叠/展开。
- **请求编号体系**：每个 LLM 请求全局编号（#1、#2…），显示 provider/model、状态（运行/完成/报错）、**重试链**（第 N 次/最多 N 次）、单次与**累计 token**（输入/缓存读/缓存写/输出/思考分桶）。
- **压缩处理**：压缩（compaction）请求显示在独立的 "Between turns" 区段，带编号的压缩归属其轮次内，压缩本身也可回放。
- **性能设计**：虚拟滚动（仅渲染可见行）、打开时锚定当前尾部、**向前补页**加载更早历史（保留滚动位置）、流式 partial 记录实时追加、跨视图跳转（聊天里点工具卡的 Inspect 直接跳到轨迹对应记录）。

## 3. 砼智页面输出现状（对照基线）

（依据子代理 B 对 src/renderer + src/main/agent 的精读）

**已有**：
- 双通道流式：agent 模式（agent:progress IPC 事件：reasoning_start/delta/done、tool_start/done/error、text_delta、model_info）与简单聊天模式（aiAnalysis:chatStream:event）
- 思考折叠（StreamingAgentCard ReasoningBlock：运行呼吸灯 + 折叠默认前 40 字）；`<think>` 标签折叠
- 工具调用：timeline 内工具行（状态图标 + 中文标签 + 输入/结果摘要 + 点击展开原始 JSON）
- ContextIndicator 上下文占用圆环（≥80% 变红提示压缩）
- TodoPanel（LLM 计划清单 + 进度 + 优先级）、业务结果卡（配合比/优化/报价）、FileMessageCard、Workspace 文件网格
- 暂停/停止（头部按钮）、断点续跑（resumeFromCheckpoint）、插话/追加任务、审批弹窗（DecisionGate/PlanApprovalModal）
- 持久化：SQLite（Sequelize），chat_history 表含 metadata(JSON)，**assistant 消息保存时把 timeline（思考+工具过程）写入 metadata.timeline** —— 这是轨迹功能现成的数据基础！

**差距与缺陷**（代码事实）：
1. StreamingAgentCard 卡内暂停/继续/取消按钮 props 未传入（onPause/onResume/onAbort 为 undefined），点击无效——确凿缺陷
2. 无 token/耗时统计展示（只有占用百分比圆环）
3. 消息无复制/点赞点踩/单条重试
4. 无轨迹视图（timeline 只在气泡里逐条平铺展示，无时间线/搜索/检查器）
5. 双通道 reducer 逻辑重复（agent 模式 vs chatStream 模式），AgentProgressCard 已成死代码
6. 流式每帧全量重建 timeline 数组，长对话有卡顿风险
7. timeline 存在 metadata JSON 里，无独立 schema，无法做字段级查询与统计分析

## 4. DSH 值得砼智学习的地方（按价值与性价比排序）

> 排序逻辑：对砼智用户体验的提升幅度 × 实现成本。每项附建议落地形态。

**L1. 工具调用卡片升级（强烈建议，性价比最高）**
- 现状：工具行 + JSON 折叠，专业感不足
- 建议：按工具类型做专属卡片——材料查询→表格卡、配合比计算→参数卡（已有 MixDesignResultCard 可融合）、读文件→带行号卡、命令执行→终端卡、文件修改→diff 卡；统一外壳（图标+标题+摘要+状态点）
- 工作量：1 周内（组件化，复用到各业务卡）

**L2. 每轮回复统计行（小改动，专业感立增）**
- 现状：无展示；但**token 数据已在运行时采集**（DeepSeekService.js:783 从流式最后 chunk 提取 usage，:1172 挂到消息对象，ContextIndicator 的占用 % 用的就是它）
- 建议：回复尾部显示 `LLM 时长 · 工具时长 | TTFT · tok/s | in/out tokens`。只需把 usage 随 saveMessage 写入 metadata（当前 metadata 只存 timeline，见 agentActions.js:489）并在 UI 渲染；耗时需在主进程补时间戳
- 工作量：≤1 天（token 部分），计时埋点另加 1 天

**L3. 消息操作：复制/反馈/单条重试（小改动）**
- 建议：复制按钮（clipboard）、赞/踩（落库 chat_history 新字段）、单条"重新生成"（复用断点续跑机制）
- 工作量：2-3 天

**L4. 轨迹视图（核心需求，见第 5、6 章）**

**L5. 回合产出文件 chips（小改动）**
- 建议：AI 回合结束后，把该轮生成/修改的文件（配合比方案、报告、Excel 导出）聚合为可点击 chips
- 工作量：1-2 天

**L6. 上下文计量细分面板（小改动）**
- 现状：只有占用 % 圆环；建议点击弹出 system/tools/messages 三段构成 + 建议压缩按钮
- 工作量：1 天

**L7. 工程架构层（中期）**
- 插槽注册机制（新业务卡片无需改聊天主组件）、snapshot 订阅（避免全量 state 传递）、帧节流渲染（长输出流畅）
- 工作量：重构性质，建议随大版本迭代

## 5. "轨迹"功能深度剖析（DSH trajectory 机制）

### 5.1 本质
把 AI 一次完整工作过程（用户问题 → 思考 → 每次工具调用 → 中间结果 → 最终回答）变成**结构化、可检查、可搜索、可回放**的记录账本——这就是"agent 操作轨迹"（trajectory）。落到砼智场景（混凝土行业 AI 助手），它还有额外价值：**新人可以复盘老工程师的 AI 操作过程，掌握标准工作流**（详见 6.1 第 3 条）。

### 5.2 数据模型（每条记录）
`#序号 + 类型 + 一句话摘要（Markdown 转纯文本截断）+ 详情`：
- 详情面板：输入全文 / 输出全文 / 思考全文 / 工具 schema / 精确开始时间与耗时
- 度量：TTFT（首 token 时间）、token 分桶（输入/缓存读/缓存写/输出/思考）
- 错误标记：isError（失败记录红色标识）
- 稳定性：每条记录有稳定 ID（跨历史分页加载不乱序），记录间可跳转（sourceSeq）

### 5.3 时间线可视化
Chrome Network 面板交互范式：等宽/真实耗时/真实时间 4 种模式、拖选区间、滚轮缩放、点击聚焦、三车道。用户一眼看出"AI 大部分时间花在哪个环节"。

### 5.4 搜索与性能
增量全文索引（变更后 3 秒批量提交重建，源码 `SEARCH_INDEX_THROTTLE_MS=3000`）、虚拟滚动、历史分页（保留滚动位置）、流式 partial 记录实时插入。

### 5.5 数据链路（DSH 侧）
会话事件流（assistant/chunk、tool-call 等）→ **JSONL 追加日志持久化**（每个会话一个文件，zstd 压缩，chunk 合并打包省 60% 体积）→ **会话投影（session-projection）** 把事件流重组为可查询视图 → 轨迹快照构建器 → 前端 Trajectory 视图。另外 SQLite 派生索引提供全文检索。

**核心设计原则（官方架构文档原话）："模型可见即已记录"** —— 会话事件日志是唯一事实源，模型历史、回放、文本记录（transcript）、遥测、轨迹全部从事件流派生（`deriveMessages()` 投影模型历史，原始 `assistant/chunk` 事件保证回放与 UI 保真）。轨迹功能不是"额外记录"，而是**同一份日志的另一种投影**——这是它实现成本低、可靠性高的根本原因。反观砼智目前是"状态快照"模式（timeline 随消息落库），从快照做轨迹功能可行但回溯能力弱；若后续把 agent:progress 事件也落成追加日志（哪怕只存关键事件），就能获得 DSH 同等的回溯与回放能力。

### 5.6 AI 产品"轨迹"行业实践对比（网络调研）

> 注：本部分第三方产品信息为行业常识（本次会话 web_search 通道不可用，未能取得一手来源 URL），仅供方向参考；DSH 相关均为一手实测。

| 产品 | 轨迹/过程展示形态 | 说明 |
|---|---|---|
| Claude（Anthropic） | activity/提交面板 + 会话历史 | 侧边面板展示工具调用/文件改动/耗时，利于复盘 |
| Cursor | Timeline 时间线 | 每次改动存快照，可回滚、对比 diff |
| OpenAI Codex | 会话轨迹/run 记录 | agent 每步操作与日志流，可审计 |
| Gemini | 思考过程 transcript | 深度思考推理过程展示（可开关） |
| Manus | 操作回放 | 网页上回放 agent 浏览器操作步骤，演示效果好 |
| **DeepSeek Harness** | **Trajectory 视图（一手实测）** | 按轮次账本 + Overview 时间线（TTFT/解码区分）+ 检查器 + 全文搜索 + 虚拟化补页，形态最完整 |

主流做法总结：**"记录每一步操作事件 + 提供可视化回放/时间线/差分"**，时间线 + 可定位到具体步骤是提升信任与可复盘性的通用手法；是否暴露思考过程按产品定位权衡。

## 6. 砼智增加"轨迹"功能的可行性

### 6.1 需求定义（建议）
结合砼智场景，轨迹功能应包含：
1. **过程回看**：每次 AI 回复旁增加"查看轨迹"入口，展开本次工作的完整过程（思考 + 每步工具调用 + 中间数据 + 耗时）
2. **会话轨迹页**：整个会话的操作账本，按回合分组，支持搜索（如搜"配合比""开裂"）、过滤（只看失败步骤）
3. **复盘与传承**（差异化价值）：把优秀操作轨迹保存为"标准做法"，新人可跟随学习（对齐 TrainingPanel 的模型管理思路，做"操作知识库"）
4. **统计**：每步耗时、每轮 token（成本感知）

### 6.2 现状基础评估

| 维度 | 现状 | 评估 |
|---|---|---|
| 过程数据 | timeline（reasoning+tool 节点，含状态/roundIndex）已随消息存 SQLite metadata | ✅ 数据已具备，缺独立 schema |
| 流式通道 | agent:progress 事件已含 reasoning_delta/tool_start/done/error | ✅ 已具备 |
| 耗时/token | token 已在运行时采集（DeepSeek 流式 usage，DeepSeekService.js:783/1172）但未落库；每步耗时未记录 | ⚠️ 需补落库 + 计时埋点 |
| 前端框架 | React + antd，已有 StreamingAgentCard/TodoPanel 等卡片体系 | ✅ 具备 |
| 搜索能力 | 无全文索引（SQLite 内可做 LIKE/FTS5） | ⚠️ 需新增 |
| 存储 | SQLite（Sequelize）已在用 | ✅ 扩展表即可 |
| 性能 | timeline 数组全量重建 | ⚠️ 轨迹页需虚拟滚动或分页 |

### 6.3 分阶段方案与工作量

**阶段 1：基础轨迹视图（MVP，约 2-3 天）**
- 数据：新增 `trajectory_steps` 表（会话ID、回合、步骤、类型、标题、摘要、状态、开始/结束时间、JSON 详情），主进程在事件发生时写库（或继续用 metadata.timeline 解析，先不改主进程）
- UI：会话页顶部 tab"轨迹"，按回合分组的步骤账本列表；每行：图标+摘要+耗时+状态点；点击展开详情（输入/输出/思考全文）；失败红色标识
- 产出：可查看、可复盘的基础轨迹页

**阶段 2：搜索与统计（约 1 周）**
- 搜索：SQLite LIKE/FTS5 全文搜索（按内容/工具名/状态过滤）
- 统计：回合头部显示 `N 步 · 总耗时 · LLM 耗时 · token 消耗`；每步精确耗时（主进程补时间戳）
- 折叠控制：全部展开/折叠；只看失败/只看工具
- 跨视图跳转：聊天里点某步骤 → 轨迹页定位该记录

**阶段 3：时间线可视化与传承（约 2-3 周）**
- Chrome Network 风格时间线（4 种模式、缩放、区间聚焦）——可直接参考 DSH 的 `deriveTrajectoryTimeline` 纯函数设计
- 虚拟滚动/分页加载长会话
- ~~差异价值："保存为标准做法"——轨迹一键存为模板~~【2026-08-14 老板决策：**暂不考虑**；现有技能管理已支持在会话中让 AI 创建技能（create_skill 工具 + 用户技能目录 + 技能中心），"标准做法知识库"需求已被该能力覆盖，不重复建设】

### 6.4 技术风险与对策

| 风险 | 对策 |
|---|---|
| 主进程改动影响稳定性 | 阶段 1 先只读现有 metadata.timeline 解析，不动主进程；阶段 2 再加埋点 |
| 长会话性能（千级步骤） | 虚拟滚动（复用 antd Table 虚拟或 react-window）+ 分页加载 |
| timeline 数据结构不统一（双通道） | 顺带统一两套 reducer（L7 工程项），或轨迹层做归一化适配器 |
| 搜索中文分词 | SQLite FTS5 对中文支持弱，先用 LIKE + 记录级过滤，必要时引入轻量分词（如 jieba 的 WASM 版） |
| 隐私 | 轨迹数据仅本地存储，导出功能需用户确认 |

### 6.5 建议路线图
1. 本周：L2 统计行 + L3 复制/反馈（小步快跑，用户立刻有感）
2. 下两周：阶段 1 + L1 工具卡升级（用户感知最强的两件事）
3. 一个月：阶段 2、3（搜索、时间线）【阶段 3 的"标准做法知识库"已按老板决策暂缓，见 6.3】

## 7. 结论

1. **DSH 的页面输出**是当前 AI 工具界第一梯队的水准：工具卡体系、统计行、思考折叠、轨迹视图、插槽架构，每一项都有成熟可参考的代码实现（MIT 协议，可直接借鉴）。
2. **砼智的差距主要在"呈现层细节"而非"能力层"**：数据（timeline）和通道（IPC 流式）已具备，缺的是展示形态与统计——这也是投入产出比最高的改进方向。
3. **轨迹功能：可行，推荐做**。它把砼智现有 timeline 数据升级为可搜索、可回放、可传承的操作账本，是差异化竞争力（行业 AI 助手普遍没有），且分阶段实施风险可控：MVP 2-3 天、完整版 1 个月左右。
4. 建议优先落地：统计行 + 消息操作（本周）→ 基础轨迹视图 + 工具卡升级（两周）→ 搜索/时间线（一个月）。【"标准做法知识库"按老板决策暂缓，现有技能管理（会话内 create_skill）已覆盖】
