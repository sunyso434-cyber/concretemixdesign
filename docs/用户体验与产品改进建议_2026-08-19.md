# 砼智 v0.9.x 用户体验与产品改进建议

> 视角：砼智资深用户（PC 端 + 手机端深度使用）＋ 混凝土生产企业技术人员
> 日期：2026-08-19
> 前提：已核对现有功能（配合比设计/成本优化/合规审查/强度预测/试配闭环/材料批次/生产供应计划/手机远程对话/知识库等），以下建议均为与现有能力的真实缺口，非重复项。

---

## 建议一（P0）：配合比全生命周期「复核 → 批准 → 下发 → 停用」审批流

**痛点场景**
- AI 几分钟就能出一版配比，但企业流程要求"技术人员复核后才能下发生产"（你们自己的应用心得文档也写了这条底线）。现在方案状态只是一个字符串 `未验证/已验证`，没有强制流程。
- 生产供应计划绑定配合比时**不检查是否已批准**，任何人随时能把未复核的 AI 配比挂到当日生产计划上。
- 一旦出质量问题（比如强度不合格、和易性问题），无法回答"这版配比是谁批准的、批的时候是什么内容"。

**需求**
1. MixDesign.status 升级为状态机：`草稿 → 待复核 → 已批准 → 已停用`，并提供 `退回（附意见）`。
2. 审批动作记录到审计（AuditLog 现有 actor 只有 'ai'，扩展为人工账号：谁批的、什么时间、意见、before/after 快照）。
3. 已批准的配比**禁止直接编辑**——修改只能"新建修订版"，原版本保留，形成版本链，可追溯"某月某日某项目用的第几版"。
4. 生产供应计划（DailyPlan.boundMixDesignId）与销售报价只允许绑定 `已批准` 状态的配比，未批准的在选择器里置灰并提示。

**落地范围**：`src/main/db/models/MixDesign.js`、`AuditLogService`、`productionPlanHandler`、方案管理页 + 手机端（只读查看审批状态）。

---

## 建议二（P0）：生产配合比换算（砂石含水率修正）—— 试验室配比 → 生产配比

**痛点场景**
- 设计和试配出来的是**干基配合比**。搅拌楼每天要根据砂石含水率把称量值换算成**实际生产配合比**（含水修正砂、石用量并扣减用水量），这是试验室/操作员**每天必做**的手工活。
- 目前全是手算或 Excel，容易算错；算完和"今日计划"、和配合比通知单脱节，还要再人工誊抄。

**需求**
1. 新技能 + 表单：输入细/粗骨料含水率（支持从质检日报 Excel 批量导入）→ 输出 `1m³` 与指定盘方（如 2m³）的实际称量配比，含用水量修正和容重校核。
2. 含水率变更场景：同一配比多组含水率对比，直接生成"生产配合比通知单"（docx），一键写入当日生产计划对应车次备注。
3. 与"建议六"的材料需用计划联动：用**修正后**的生产用量做 BOM 汇总，而不是干基用量。

**落地范围**：新 skill（`convert_production_mix` 之类）+ 表单页/结果卡片，复用 `mix-design.js` 的配比数据结构和 `workspace_writeFile` 出报告。

## 建议三（P1）：手机端补"现场高频查询"与语音输入（不止是对话）

**痛点场景**
- 手机端目前只有 Agent 对话（设计文档明确"不做独立业务页面"）。但现场高频场景是：搅拌楼/工地/夜间值班，想**秒查**"今天 C30 计划几车""当前生效的 C30 配比是多少""砂石最新价格"，每次都要打字问 AI，慢且费流量。
- 现场环境（戴手套、搅拌楼噪音）打字困难；设计文档把语音输入列为暂不做，但这是移动端使用率的第一阻碍。

**需求**
1. 手机 App 增加只读「快捷查询」页：今日生产计划、当前生效配比、材料价格、最近试配记录四张卡片，数据由电脑端远程 API 提供（只读，不增加电脑端业务改动）。
2. 语音输入转文字（手机端本地识别，文字走现有 agent:run 通道）。
3. 电脑端不在线时，手机端明确提示"电脑未连接/任务不可用"，而不是发送后静默失败或一直转圈。

**落地范围**：`RemoteWorkspaceApi` 扩展或新增 `RemoteQueryApi`；Flutter 新增页面 + `speech_to_text`；`ConnectionService` 增加断线原因透出。

## 建议四（P1）：材料价格版本化 + 成本/报价联动预警

**痛点场景**
- 材料价格是**全局单一值、手动改**。现实是水泥、砂石价格每周都在动，改一次价格，所有历史方案的 `totalCost`、已报价项目的利润**全部跟着变**，且没有任何提示——昨天报出去的价，今天成本已经变了却没人知道。
- 报价单用的是"当前价"，无法回溯"当时报价是按什么价格算的"，客户对账时说不清。

**需求**
1. 材料价格加**生效日期历史**（新表 `MaterialPriceHistory`），支持 Excel 批量更新（可与质检日报含水率同表导入）。
2. 价格变更后自动列出"受影响方案 + 受影响在库报价 + 成本变化额"，提示是否需要重算报价（不自动改，人工确认）。
3. 销售报价保存时**快照当时材料价格与成本明细**（现有 `SalesQuoteHistory` 扩展 priceSnapshot），支持按报价单追溯当时成本。

**落地范围**：`Material`/`SalesQuoteHistory` 模型扩展、`material-manage.js` 技能、报价相关技能、设置页导入向导。

---

## 建议五（P2）：强度预测扩展到多龄期（3d/7d/28d）＋ 生产强度自动回流

**痛点场景**
- 现在只预测 28d 强度。但生产上 3d/7d 试块数据**先出来**，现场最想干的是用早期强度反推 28d（成熟度法/回归）——提前决定"这批能不能继续浇筑、要不要调配比"，而不是干等一个月。
- 试配/生产实际强度目前要靠人手动录，训练集增长慢。

**需求**
1. 预测目标扩展 3d/7d/28d（或至少"7d → 28d 推算"），输出强度发展曲线。
2. 试配记录增加龄期维度，实际生产强度数据可批量导入并自动进入重训数据集；模型按季度自动提醒重训（文档里已有的建议，落到产品里）。
3. 强度预测结果与合规审查联动：预测不达标时给出调整建议（提标号/调水胶比）。

**落地范围**：训练数据 schema 加龄期列、`retrain-model.js` 多目标、`performance-prediction.js` 输出扩展、`record-trial-test.js` 字段扩展。

## 建议六（P2）：生产供应计划自动生成「材料需用计划」（BOM 汇总）

**痛点场景**
- 已经有了"每日计划 + 绑定配合比"，但**没有自动汇总**当天/本周水泥、砂、石、外加剂总需用量。目前材料员靠人工估，容易多订压库存或少订断供。
- 这是从"调度计划"走向"采购/库存"最自然的一步，数据现成，缺的只是聚合。

**需求**
1. 按日期范围（默认今日/本周）汇总各材料需用量：Σ(计划方量 × 该标号配比用量)，**使用生产配合比换算后的用量**（联动建议二）。
2. 与现有库存/在途对比（先做手动录入库存，后续可对接搅拌站系统），输出"需采购量建议"。
3. 作为"每日计划"页的一个汇总区块，或导出 Excel/报告。

**落地范围**：新查询服务聚合 `DailyPlan × MixDesign`，前端在 ProductionPlanPage 加汇总区块。

---

## 建议七（P2）：多角色权限 + 定时自动备份（企业化基础能力）

**痛点场景**
- 单机单用户。企业里技术员、试验室主任、业务员共用或轮流用，现在**谁都能改价格、删方案、改配比**，出问题无法界定责任（AuditLog 的 actor 只有 'ai'）。
- 数据只有手动备份；电脑故障/中病毒就是全部数据丢失。版本升级也没有任何更新检查/通知渠道。

**需求**
1. 轻量角色：操作员（只读+查询）/ 技术员（设计/试配）/ 管理员（价格、审批、删除、备份），关键动作记登录账号。
2. 定时自动备份：每日备份 + 保留最近 N 份（复用现有按天日志清理的思路），支持一键导出到移动硬盘/网盘。
3. 应用内升级检查：启动时请求版本号，提示下载新安装包（现有 `publish: null`，可先做"手动检查更新"）。

**落地范围**：登录/角色表、`AuditLog.actor` 扩展、`backup.js` 定时化、设置页。

---

## 与现有能力的边界（避免重复建设的核对）

已确认存在、本建议不重复：试配"设计→试配→复盘"闭环、材料批次管理、生产供应计划（每日计划/产能/距离/每车明细）、手机远程双端同步对话、上下文压缩、成本优化、合规审查、模型重训/回滚、MinerU 解析、Wiki 知识库。建议二/四/六分别补齐的是：**干湿基换算、价格历史、材料 BOM**，这三块当前代码里都没有（已检索确认无"含水率/生产配合比"相关技能，无价格批量/历史功能）。

---

## 优先级总结

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | ① 审批流 ② 生产配合比换算 | 直接关系质量责任与每日生产，是"能不能进厂里正式用"的门槛 |
| P1 | ③ 手机快捷查询+语音 ④ 价格版本化+预警 | 一线使用体验与经营风险，提升使用率最明显 |
| P2 | ⑤ 多龄期强度 ⑥ 材料需用计划 ⑦ 权限+自动备份 | 深水区能力，随数据积累逐步上 |
