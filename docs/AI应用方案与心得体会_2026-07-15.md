# AI 在混凝土配合比设计中的应用方案与心得体会

> 整理日期：2026-07-15
> 应用项目：砼智 Concrete Agent（v10.10.12，基于 Electron + React 自研）
> 文档定位：技术成果汇报 + 复盘心得

---

## 一、背景（为什么要做这件事？）

### 1. 原工作场景描述

| 环节 | 原工作方式 | 关键痛点 |
|------|------------|----------|
| **配合比设计** | 技术人员查规范、手算水胶比 → 查表定砂率 → 反复试配调整 | 单方案手算 1~2 小时；不同原材料要重新算；全凭经验调系数 |
| **成本优化** | 经验丰富的老师傅凭"记忆"挑几组材料组合人工比价 | 只能比较 3~5 个候选方案；掺合料组合爆炸时凭直觉漏掉最优解 |
| **性能预测** | 经验估算 + 实际试块 28 天后才知道强度 | 强度预测滞后 28 天；坍落度/减水剂掺量靠经验拍脑袋 |
| **质量分析** | 技术人员拿到试块照片/检测报告凭经验判断 | 对知识储备要求高；新人难上手；图片资料无法批量处理 |
| **技术资料管理** | 技术人员各自归纳整理 Word/Excel，存个人电脑 | 资料散落、查找困难；版本混乱；难以形成体系 |

### 2. 存在的主要问题

1. **手算效率低，材料对应性差**：单个配合比计算 1~2 小时，材料替换或强度调整要重算 90% 的步骤。
2. **成本优化策略考虑不完全**：人工只能比较 3~5 个候选，掺合料种类一多就漏掉最优组合。
3. **性能预测靠经验**：减水剂掺量、坍落度、强度全凭"老师傅手感"，新人复制困难。
4. **质量分析依赖经验**：混凝土表面裂缝、试块缺陷需要高年资技术人员才能准确判断。
5. **技术资料散乱**：配合比表、检测报告、规范文件散落在各人电脑里，难以检索复用。

## 二、AI 应用方案（我是怎么做的？）

### 1. 整体思路

四层架构，把 AI 嵌入到"原材料库 → 设计计算 → 性能预测 → 报告输出"全链路：

```
┌──────────────────────────────────────────────────────────────┐
│  L4 报告层：workspace_writeFile 一键生成 docx/xlsx/md 报告  │
├──────────────────────────────────────────────────────────────┤
│  L3 智能层：DeepSeek LLM Agent（自动规划 + 技能调度）         │
├──────────────────────────────────────────────────────────────┤
│  L2 技能层：18 个内置技能 + 用户自建技能（业务计算）         │
├──────────────────────────────────────────────────────────────┤
│  L1 数据层：材料库 + 配合比库 + 训练样本库（SQLite）          │
└──────────────────────────────────────────────────────────────┘
```

**核心思想**：LLM 只负责"听懂人话 + 决定调哪个技能"，业务计算交给确定性的代码模块，避免大模型"幻觉"导致计算错误。

### 2. 关键实施步骤

#### ① 数据层：原材料库 + JGJ55 规范编码化

- **材料库覆盖** 8 大类（水泥/粉煤灰/矿渣粉/锂渣/复合粉/砂/石/减水剂），每条记录至少 8 项业务关键指标（密度、活性指数、需水比/流动度比、细度模数等）。
- **JGJ 55 规范代码化**：13 项标准参数（回归系数、强度标准差、减水剂掺量等）支持自定义修改和重置；支持绝对体积法/质量法两种计算方法。
- **本地化部署**：SQLite + Sequelize ORM，数据不出企业。

#### ② 技能层：18 个内置技能，LLM 只调度不计算

技能按职责分 6 类：**核心计算**（配合比计算、成本优化）、**性能预测**（XGBoost）、**视觉分析**（缺陷照片/OCR）、**知识检索**（RAG）、**文档生成**（docx/xlsx/md）、**辅助管理**（材料/参数/配合比 CRUD + 元能力 + 报价）。

每个技能都有标准 Schema 描述，LLM 通过 system prompt 看到技能清单后，自主决定调用哪个。

#### ②.bis 用户方法论技能（MD 技能）— 质量诊断与创新头脑风暴

除了内置 JS 技能，平台还支持**用户自定义 MD 方法论技能**（`~/.concrete-mixdesign/skills/*.md`），采用 `trigger_mode: soft` 软触发——LLM 看到相关关键词自动应用整套方法论。

**应用示例 1：质量缺陷诊断**（`quality_diagnose.md`，v1.0.0）

老板咨询混凝土质量问题（裂缝、蜂窝、强度不足、抗渗不足等）时触发，覆盖 **13 种缺陷**：

- **A 组看图为主**（5 种）：麻面、色差、缺棱掉角、错台、起灰
- **B 组综合推理**（5 种）：裂缝、蜂窝、狗洞、露筋、强度不足
- **C 组性能类**（3 种）：抗渗不足、抗冻不足、弹性模量不足

诊断流程严格走 **10 步**：

1. **看图** → `analyze_concrete_image` 客观提取
2. **通用项问诊**（必问 5 项：发生部位/发现时间/分布特征/天气/缺陷类型）
3. **粗判后查 wiki**（必查 1-2 次）
4. **专项项问诊**（按粗判类型动态加 2-5 项）
5. **综合推理**（查规范 + 定性 + 排除其他类型）
6. **第一性原理分析**（AI 内部用，物理/化学/力学机制）
7. **5Why + 4M1E 根因分析**
8. **对抗式审查**（AI 内部用，反例检验 + 替代解释 + 多角色视角）
9. **处理建议 + 预防措施**
10. **生成报告**（7 段 + 置信度评分）

**核心机制**：
- 问诊式对话（一次一问，不允许 form 模式）
- "不清楚"处理：B 引导回忆 → C 教用户查 → 跳过 + 标注
- wiki 7 个嵌入点（看图后/收通用项/粗判后/综合推理/根因分析/出建议/出预防）
- 第一性原理 + 对抗式审查**只用于内部推理，不展示在报告里**
- 7 段报告模板（信息完整度 → 缺陷概况 → 类型判断 → 根因 → 短期建议 → 长期预防 → 参考依据）

**应用示例 2：混凝土创新头脑风暴**（`concrete_innovation_brainstorm.md`，v2.1.0）

老板提出创新需求（低碳/绿色混凝土、高耐久方案、新材料应用、配合比优化、成本控制、新型检测方法等）时触发，走 **4 阶段探索**：

1. **探索上下文**（workspace_search + list_available_materials）
2. **澄清需求**（一次一问，目标 → 约束 → 成功标准）
3. **提出 3-5 个方向**（每个含价值/难度/数据，让老板选）
4. **深度探索**（4 轮 ask_user：现状 → 需求 → 细节 → 方案）

输出 `reports/YYYY-MM-DD-<topic>-brainstorm.md` 设计文档（含背景/选定方向/配合比建议/成本预估/风险评估/落地步骤），老板审查通过才算完成。

**价值**：把"凭经验做创新方案"变成"4 阶段结构化方法论"，每个创新都过流程，避免漏掉关键因素。

#### ②.ter 蓝图技能 — 自定义行业规范编码

**痛点**：不同企业/项目要遵守不同行业规范（JGJ/T 283 自密实混凝土、铁路、公路、水工等），通用 `calculate_mix_design` 只能覆盖 JGJ 55。**蓝图技能**让用户把任意规范编码成 YAML，LLM 即可调用。

**蓝图结构**（一个目录三件套）：

```
~/.concrete-mixdesign/skills/<skill_name>/
├── meta.yaml          # 元数据 + UI 参数表单（name/description/parameters[]）
├── blueprint.yaml     # 业务逻辑（steps[]，每步 type: input/formula/material/output/tableLookup/ifElse/const）
└── tables/            # 可选：查表数据（JSON）
```

**从创建到使用，5 步走完**：

```
老板："我要做个自密实混凝土配合比技能"
  ↓
① 准备规范 → prepare_blueprint_authoring（注入蓝图创作规范全文）
  ↓
② 生成蓝图 → LLM 在对话中生成 rawBlueprint（含 meta.yaml + blueprint.yaml + tables/ 分段）
  ↓
③ 落盘校验 → create_skill(type='tool', subType='blueprint', rawBlueprint=...)
              内部解析 → 校验 → 试算 → 写到 ~/.concrete-mixdesign/skills/<name>/
  ↓
④ 自动加载 → blueprint-loader 扫描用户目录 → SkillRegistry 注册
  ↓
⑤ 老板使用 → "用 scc_mixdesign 设计 C50 自密实" → LLM 触发 → BlueprintEngine 执行
              input → formula → material → output → 返回配合比
```

**真实例子**：`scc_mixdesign`（自密实混凝土，v3.1.0）按 JGJ/T 283-2012 第 5.2.1-4/-6/-7 条设计，覆盖 C30~C80、SF1~SF3、VS1~VS2 全规格，单价可覆盖默认值，已上线使用。

**核心引擎**（[src/main/services/BlueprintEngine/](src/main/services/BlueprintEngine/)）：7 类 handler（input/formula/tableLookup/material/output/ifElse/const）+ FormulaParser（公式引擎）+ TableInterpolator（查表插值）+ MaterialChooser（材料选择）+ AuditLogger（全链路审计）。

**价值**：让"行业规范→代码→AI 可调用技能"形成闭环，新人按规范落地不用从零写代码。

#### ③ 模型层：3 个 XGBoost 预测模型

| 目标 | 5-fold CV R² | 5-fold CV RMSE |
|------|---:|---:|
| 28 天抗压强度 | 0.61 | 7.21 MPa |
| 减水剂掺量 | 0.58 | 0.31 % |
| 容重 | 0.70 | 10.73 kg/m³ |

特征向量 35 维（配合比参数 + 材料使用标志 + 材料属性 + 养护条件 + 坍落度）。**关键技术**：3 个目标用不同特征子集训练，防止数据泄漏（例如减水剂掺量预测时强制将"自身掺量"特征置 -1，防恒等映射）。

#### ④ 智能层：LLM Agent 调度 + RAG 工作区

**DeepSeek API** 作为大脑，负责理解需求 → 选择技能 → 组合输出 → 追问缺失参数。基础设施含 SkillRegistry、SkillExecutor、AgentOrchestrator、SystemPromptBuilder 等模块。

**工作区（RAG）** 是系统的"记忆库"，让 LLM 引用企业内部的检测报告、规范文件、客户图纸：

- 工作区目录自动初始化（`wiki/`、`reports/`、`chat-history/`、`raw/{pdf,docx,xlsx,md,txt,images,...}/`）
- 文件拖入自动入库：reader 解析 → WikiEngine 写 wiki → SummaryExtractor 生成摘要 → KGExtractor 抽取实体关系三元组
- 10 个 workspace 伪技能供 LLM 调用：search（BM25）/ grep（正则）/ readPage / ingest / writeFile / listFiles / lint / searchGraph（知识图谱）/ readRaw / organize
- 双路检索：BM25 语义匹配 + 知识图谱三元组查询

#### ⑤ 输出层：5 类报告 Skill 矩阵

老板的典型 5 类报告，按以下 Skill 顺序调用（软约束，写在 system prompt）：

1. **配合比设计报告** → calculate → predict → check_compliance
2. **多方案对比** → calculate × N → cost_optimization
3. **报价单** → calculate → prepare_quote_draft
4. **原材料检测报告** → predict + check
5. **PDF 知识源报告** → 仅 workspace_search / readPage

#### ⑥ 自学习：用户偏好自动沉淀

监听工具调用事件，通过 PatternDetector 识别用户材料/参数偏好。高置信度建议（≥0.95）自动回写到 agent.md 的"业务规则"段；低置信度建议在 UI 提示用户手动采纳。

## 三、应用成果

### 1. 效率提升

> 说明：下表为当前项目开发验证和内部流程估算，不是经过统一样本、重复测量形成的正式对照试验；“提升幅度”仅用于说明流程变化，不代表模型准确率。

| 场景 | 原方式耗时 | AI 辅助后耗时 | 内部估算 |
|------|----------|------------|---------|
| 单个配合比计算 | 1~2 小时 | < 10 秒 | 流程耗时显著缩短 |
| 成本优化（10 种材料候选） | 半天（人工比 3~5 个） | 5 阶段网格搜索数分钟 | 可扩大候选方案覆盖范围 |
| 性能预测（强度/减水剂/容重） | 等 28 天试块 | < 1 秒 | 可即时给出预测，不替代实测 |
| 配合比方案报告（docx） | 半天整理 | < 1 分钟 | 自动生成初稿，仍需人工复核 |
| 多方案对比分析 | 1 天 | 数分钟 + 自动分类 | 减少人工整理工作 |
| JGJ55 参数校对 | 翻规范 + 核对 | LLM 调用 `list_jgj55_params` | 提高参数查询效率 |

### 2. 其他收益

- **新人门槛大幅降低**：之前需要 3~5 年经验才能独立做配合比，现在按对话引导即可完成 C20~C50 全等级。
- **决策可追溯**：每个配合比都有 draftId → 自动保存草稿，方案比对/复核方便。
- **资料集中化**：PDF 检测报告、规范文件、客户图纸统一入工作区，BM25 + 知识图谱双路检索。
- **AI 越用越懂你**：Learning Service 自动学习用户偏好（材料选择、参数范围），2~3 次后 LLM 自动套用。

### 3. 成果证明（重要）

- **软件版本**：已迭代至 v10.10.12，累计形成 100+ 次代码提交。
- **代码规模**：截至 2026-07-15，代码关系图统计约 452 个源文件、3.9 万条代码关系。
- **功能模块**：18 个内置技能 + 用户自定义 MD 方法论技能 + 蓝图技能 + 3 个 ML 模型 + RAG 知识库。
- **使用记录**：软件已实现"自动保存草稿 + 历史配合比查询"，单台机器可积累上千条配合比数据。
- **使用反馈说明**：当前缺少可追溯的原始访谈记录、测试样本和统计口径，因此本稿暂不把口头反馈作为正式成果证据；后续应通过任务计时、方案复核记录和用户访谈表补充。

## 四、可推广性建议

### 1. 本成果是否可以推广？

**可以推广，但需要满足以下前置条件**：

- ✅ **业务场景匹配**：本系统适用于混凝土搅拌站/外加剂厂/预制构件厂等需要日常做配合比设计的单位。
- ⚠️ **材料库初始化**：每个企业需录入自己的原材料数据（XGBoost 模型对材料属性敏感）。
- ⚠️ **训练样本积累**：预测模型精度依赖历史数据量，建议至少积累 200+ 条历史配合比-性能数据再训练。
- ⚠️ **算力/网络**：LLM 调用需联网（或本地部署 DeepSeek），XGBoost 预测本地 ONNX Runtime 即可。

### 2. 推广时需要哪些条件？

| 类别 | 具体条件 |
|------|----------|
| **硬件** | 普通 PC（i5/16G 即可）；联网环境（LLM API） |
| **数据** | 完整原材料库（8 大类）；≥ 200 条历史配合比数据；可选 PDF 检测报告 |
| **人员** | 1 名技术员负责材料库维护 + 模型再训练；不需要专业 AI 工程师 |
| **流程** | 先固化 3~5 个月使用习惯 → 收集反馈 → 调整 JGJ55 参数和偏好 → 半年后模型达到生产可用精度 |
| **合规** | 配合比设计结果需技术人员复核才能下发生产（AI 是助手，不是替代） |

**推广优先级建议**：
1. **首选**：本企业其他分厂/同集团兄弟单位（数据基础相似，迁移成本最低）
2. **次选**：同区域混凝土搅拌站（材料体系相近）
3. **谨慎**：跨区域、跨材料体系的企业（需要重新积累训练数据）

## 五、心得体会与建议

### 1. 使用 AI 工具的心得

#### 心得 ①：业务确定性 + AI 灵活性是最佳组合

> **LLM 只做"听懂人话 + 调度技能"，业务计算交给代码。**

早期版本曾尝试让 LLM 直接算水胶比，结果出现 0.42 和 0.41 错算的“幻觉”案例。后来改成“LLM 调度 `calculate_mix_design` 技能 → JS 代码执行 JGJ55 公式”，使同一输入下的公式计算结果保持确定且可复现；输入数据、规范参数和最终方案仍需技术人员复核。

#### 心得 ②：模型效果取决于数据质量，不取决于算法复杂度

XGBoost 在 105 条训练样本上的内部 5-fold 交叉验证 R² 为 0.61~0.70，可作为当前数据条件下的模型基线；该结果尚不能替代独立测试集和现场试验验证。**真正难的不是调参，是数据采集**：
- 早期把"坍落度"作为预测目标，结果坍落度是被减水剂掺量决定的（恒等映射）→ 改用减水剂掺量作为目标
- 早期把"减水剂掺量"作为特征训练，导致模型学不到坍落度影响 → 改用特征子集 + 强制 -1 防泄漏

#### 心得 ③：AI 应用是渐进式改造，不是一锤子买卖

本项目从 v1.0 走到 v10.10.12，经历了：
- 早期：搭框架 + 单点技能
- 中期：补 RAG 检索 + 多步 Agent 编排
- 后期：打磨 system prompt + 数据泄漏修复 + 学习能力

**每个版本都是上一个版本的增量改进**，不是一开始就有完整规划。

#### 心得 ④：用户视角的可解释性 > 技术上的先进性

宁愿牺牲 5% 的预测精度，也要让用户看到：
- "这个配合比用的哪条规范"
- "AI 为什么这么调"
- "成本优化对比了哪些组合"

代码里大量 `logger.info` 和 `error.hint` 都是为了这个目标。

#### 心得 ⑤：本地化部署是企业级 AI 应用的底线

- LLM 当前可调用 DeepSeek API，也可切换为企业内网模型
- XGBoost 模型 ONNX Runtime 本地推理
- SQLite 本地数据库

SQLite 业务数据和 XGBoost 推理默认留在本机；但使用外部 LLM API 时，发送给模型的提示词和上下文会离开企业网络，不能笼统表述为“数据不出企业”。生产部署应采用字段脱敏、最小化上下文、调用审计，或改用企业内网模型。

### 2. 对后续 AI 活动的建议

| 维度 | 建议 |
|------|------|
| **数据治理** | 建立原材料数据录入的标准化流程（专人审核），避免脏数据进入训练集 |
| **模型迭代** | 每季度用最新配合比数据重训 XGBoost，目标是把 R² 从 0.6 提升到 0.8+ |
| **场景扩展** | 考虑引入耐久性预测、抗渗预测等更多目标（看业务需求） |
| **多模态** | 视觉模型（缺陷识别）目前准确率受限于通用视觉模型，建议后续用混凝土行业数据微调 |
| **业务融合** | AI 不能脱离业务，建议每月和资深技术人员开"配合比评审会"，把 AI 输出和实际试块比对 |
| **知识沉淀** | 把每次"AI 算错被纠正"的案例写入 CorrectionRule 表，作为后续 Few-shot 提示 |
| **人才培养** | 鼓励技术人员学 SQL、Python 基础，能看懂 XGBoost 特征重要性、读懂 LLM 日志 |
| **合规底线** | AI 输出必须经过人工复核才能进入生产；建议加"AI 建议 ≠ 工艺决定"的免责声明 |
